# Decision 025: Cross-Site Trend Alerts and Watchlist Monitoring Integration

## Date

2026-05-08

## Status

Accepted

## Context

Milestone 25 introduced cross-site analytics trend snapshots that persist point-in-time analytics and detect material changes. However, trend changes were only visible through CSV reports and dashboard tables. There was no mechanism to flag specific changes that need human review, track alert lifecycle, or integrate trend signals into watchlist monitoring.

## Decision

### Add cross-site trend alerts after trend snapshots

Alerts are generated by comparing consecutive analytics snapshots and applying centralized rules. This builds directly on Milestone 25 snapshot infrastructure rather than re-computing analytics from scratch.

### Alerts are neutral review signals

All alert messages use neutral language. Alerts flag data changes that may warrant human review. They do not make purchase recommendations, infer seller intent, or suggest market timing.

### Alert history is preserved

The `cross_site_trend_alerts` table stores the full alert lifecycle. Alerts move through open, acknowledged, resolved, and archived states. Historical alerts are never deleted, providing a complete audit trail of cross-site data changes.

### Watchlist state is not automatically changed

Cross-site trend alerts do not modify `active_watch_status`, `user_decision`, `user_notes`, `watch_priority`, or any other watchlist field. Alert summary fields are available for report integration but require human action to affect watchlist state.

### Quiet Score gatekeeper is unchanged

Cross-site trend alerts do not influence or override the Quiet Score gatekeeper. The `apply_quiet_gatekeeper` function is not called or imported by the alert module.

### Walkability remains excluded

Walkability-type information is not part of the cross-site trend alerts scope.

### Duplicate prevention

Open alerts are deduplicated by property_id + alert_type + snapshot_id. This prevents the same alert from being created multiple times when the generation command is re-run against the same snapshots.

### Centralized alert rules

All alert rules and severity thresholds are defined in a single location (`DEFAULT_RULES` in `cross_site_trend_alerts.py`). This makes future threshold tuning straightforward without scattered logic.

## Consequences

### Positive

- Material trend changes are surfaced as actionable alerts with severity levels
- Alert lifecycle tracking provides accountability for review decisions
- Centralized rules are easy to tune as operational experience grows
- Watchlist monitoring integration provides per-property alert context
- Dashboard shows alert status at a glance with filtering
- CSV export enables offline alert review and analysis
- No automated state changes protect human-in-the-loop workflow

### Negative

- Alert volume may be high during initial deployment if many properties have material changes
- Severity thresholds are initial heuristics that may need tuning
- Alert table grows over time (one row per alert per property per snapshot)
